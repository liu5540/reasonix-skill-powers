# 头脑风暴：将想法转化为设计

通过自然的协作对话，帮助将想法转化为完整的设计和规格文档。

首先了解当前项目上下文，然后一次问一个问题来完善想法。一旦理解要构建什么，呈现设计并获得用户批准。

## 硬性关卡
在呈现设计并获得用户批准之前，禁止调用任何实现技能、写任何代码、搭建任何项目或采取任何实现行动。适用于每个项目，无论看起来多简单。

## 反模式："这个太简单了不需要设计"

每个项目都要走这个过程。一个待办列表、一个单函数工具、一个配置变更——全部都算。"简单"项目是未经审视的假设造成最多浪费的地方。设计可以简短（真正简单的项目几句话就好），但必须呈现并获批。

## 检查清单

必须逐项完成：

1. **探索项目上下文** — 检查文件、文档、最近提交
2. **提出澄清问题** — 一次一个，理解目的/约束/成功标准
3. **提出 2-3 种方案** — 包含权衡和你的推荐
4. **呈现设计** — 按复杂度分段，每段后获取用户批准
5. **写入设计文档** — 保存到 `docs/superpowers/specs/<当前日期>-<主题>-design.md` 并提交
6. **规格自审** — 快速检查占位符、矛盾、歧义、范围
7. **用户审查书面规格** — 请用户查看规格文件，确认后再继续
8. **过渡到实现** — 调用 `writing-plans` 技能创建实现计划

## 过程流程

```
探索项目上下文 → 提出澄清问题 → 提出2-3种方案 → 呈现设计分段 → 
用户批准设计？→ 否 → 修改后重新呈现
              → 是 → 写入设计文档 → 规格自审 → 用户审查规格？
                → 更改请求 → 修改设计文档
                → 批准 → 调用 writing-plans 技能
```

**最终状态是调用 writing-plans。** 在头脑风暴之后，只调用 writing-plans。

## 过程详解

**理解想法：**
- 首先检查当前项目状态（文件、文档、最近提交）
- 在询问细节前先评估范围：如果请求涉及多个独立子系统（如"构建一个包含聊天、文件存储、计费和分析的平台"），立即标记。不要花时间细化需要先分解的项目。
- 如果项目太大无法放入单个规格，帮助用户分解为子项目：独立的部分有哪些、如何关联、按什么顺序构建？然后按正常设计流程对第一个子项目进行头脑风暴。每个子项目有自己的 规格 → 计划 → 实现 周期。
- 对于范围合适的项目，一次问一个问题来完善想法
- 尽可能使用选择题，问答题也可以
- 每条消息只问一个问题——如果某个主题需要更多探索，拆成多个问题
- 聚焦理解：目的、约束、成功标准

**探索方案：**
- 提出 2-3 种不同方案并说明权衡
- 对话式呈现选项，给出你的推荐和理由
- 以推荐的选项开头，解释为什么

**呈现设计：**
- 一旦你相信理解了要构建什么，呈现设计
- 每段按其复杂度缩放：简单的话几句话，复杂的话最多200-300字
- 每段后询问是否看起来正确
- 覆盖：架构、组件、数据流、错误处理、测试
- 准备好回退澄清如果有不清楚的地方

**为隔离和清晰而设计：**
- 将系统分解为更小的单元，每个单元有一个明确的目的，通过良好定义的接口通信，可独立理解和测试
- 对每个单元应该能回答：它做什么、如何使用它、它依赖什么？
- 不看内部实现能理解一个单元做什么吗？能在不破坏消费者的情况下修改内部吗？如果不能，边界需要重新设计。
- 更小、边界清晰的单元也让你更容易操作——你能更好地推理一次能放入上下文的代码，编辑也更可靠。当文件很大时，通常是个信号说明它做太多了。

**在已有代码库中工作：**
- 在提出更改前探索当前结构。遵循已有模式。
- 当已有代码有问题时（如文件过大、边界不清晰、职责纠缠），将针对性的改进包含在设计内——就像好的开发者在工作中改进代码一样。
- 不要提出无关的重构。聚焦当前目标。

## 设计之后

**文档化：**
- 当前日期 通过 `data +%Y-%m-%d` 获取
- 将验证过的设计（规格）写入 `docs/superpowers/specs/<当前日期>-<主题>-design.md`
- 将设计文档提交到 git

**规格自审：**
写完规格文档后，用新眼光审视：

1. **占位符扫描：** 有"TBD"、"TODO"、不完整的部分或模糊的需求吗？修复它们。
2. **内部一致性：** 各部分有矛盾吗？架构与功能描述匹配吗？
3. **范围检查：** 是否足够聚焦到单个实现计划，还是需要分解？
4. **歧义检查：** 任何需求能被两种方式解读吗？如果是，选择一种并使其明确。

内联修复所有问题。不需要重新审查——修完即走。

**用户审查门：**
规格审查循环通过后，请用户查看书面规格：

> "规格已写入并提交到 `<路径>`。请审查，在开始编写实现计划前如需任何变更请告诉我。"

等待用户回应。如果他们请求更改，做出更改并重新运行规格审查循环。只有用户批准后才继续。

**实现：**
- 调用 `writing-plans` 技能创建详细的实现计划
- 禁止调用任何其他技能。writing-plans 是下一步。

## 关键原则

- **一次一个问题** — 不要用多个问题淹没用户
- **优先选择题** — 比问答题更容易回答
- **无情应用 YAGNI** — 从所有设计中移除不必要的功能
- **探索替代方案** — 在确定前始终提出 2-3 种方案
- **增量验证** — 呈现设计后获取批准再继续
- **灵活应变** — 当有不清楚的地方随时回退澄清
