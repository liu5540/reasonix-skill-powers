# 头脑风暴：将想法转化为设计

## 概述

通过协作对话将想法转化为完整设计和规格说明。先了解项目上下文，逐一提问完善想法，展示设计方案并获批准后才进入实现。

**硬性审计门槛：** 展示设计方案并获得用户批准之前，不调用任何实现技能、不写代码、不搭建项目。适用于所有项目，无论多简单。

## 反模式

"这个太简单了，不需要设计" — 每个项目都要经过此流程。简单项目恰恰是未检验假设造成最多浪费的地方。设计可以简短，但必须展示并获批准。

## 流程

1. **探索项目上下文** — 检查文件、文档、最近 commit
2. **提出澄清问题** — 每次一个，了解目的/约束/成功标准，尽量选择题
3. **提出 2-3 种方案** — 附带权衡分析和推荐，先展示推荐方案
4. **展示设计** — 按复杂度分节展示，每节后询问是否正确。涵盖：架构、组件、数据流、错误处理、测试
5. **编写设计文档** — 保存到 `docs/superpowers/specs/<current-date>-<topic>-design.md` (use ISO 8601 date, e.g. 2025-06-15) 并 commit
6. **规格自检** — 扫描占位符/TODO/矛盾/模糊点/范围，发现问题直接内联修复
7. **用户审查书面规格** — 请用户审查，要求修改则修改后重新自检，批准后继续
8. **过渡到实现** — 调用 writing-plans

## 流程控制

- 展示设计 → 用户不批准 → 修改设计，回到展示
- 编写文档 → 用户审查不通过 → 修改文档，回到自检
- 终止状态是调用 writing-plans，不调用其他技能

## 关键原则

**理解想法：**
- 先查看当前项目状态（文件、文档、commit）
- 评估范围：多个独立子系统 → 先拆分再逐个设计。每个子项目独立规格→计划→实现周期
- 范围适当 → 每次一个问题，优先选择题，每条消息一个问题
- 重点理解：目的、约束、成功标准

**探索方案：**
- 提出 2-3 种方案及权衡，附带推荐和理由
- 先展示推荐方案并解释原因

**展示设计：**
- 每个部分篇幅匹配复杂度：简单几句话，复杂最多 200-300 字
- 每个部分展示后询问是否正确
- 随时准备回头澄清不明确处

**面向隔离和清晰的设计：**
- 拆分为更小单元，每个单元有明确职责，通过良好接口通信
- 每个单元能回答：做什么、如何用、依赖什么
- 不看内部实现就能理解功能？改内部不影响调用者？否则边界需调整
- 小而专注的文件便于推理和编辑

**在现有代码库中工作：**
- 先探索现有结构，遵循已有模式
- 现有代码存在问题（文件过大、边界不清）→ 设计中包含针对性改进
- 不提议无关重构，专注服务当前目标

**规格自检：**
1. 占位符扫描：有没有"待定"、"TODO"、未完成章节？
2. 内部一致性：章节之间有矛盾？
3. 范围检查：是否聚焦到一个实现计划可覆盖？
4. 模糊性检查：需求可被两种方式理解？选一种明确写出。

发现问题直接内联修复。

## 核心原则

- 每次一个问题，不抛出多个
- 优先选择题
- 严格 YAGNI，移除不必要功能
- 始终提出 2-3 种方案
- 增量验证：展示 → 批准 → 继续
- 不明确就回头澄清
