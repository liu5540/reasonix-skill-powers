# 中文代码审查规范

## 概述

国内团队 Code Review 的平衡点：既不回避问题，又让人愿意接受反馈。

**核心原则：** 用"建议"代替"命令"，用"提问"代替"否定"，但绝不因面子放过 bug。

## 审查反馈表达方式

### 用建议代替命令

| 避免（命令式） | 推荐（建议式） |
|---------------|---------------|
| 你必须改成 X | 建议考虑用 X，因为 Y |
| 这里写错了 | 这里可能存在一个问题，是否考虑过 Z 的情况？ |
| 不要用这个方法 | 这个方法在 A 场景下可能有性能问题，可以看看 B 方案 |
| 这段代码不行 | 这段逻辑我理解得对吗？如果输入为空会怎样？ |

### 用提问代替否定

```
# 好：这里用 sync 方式读文件是出于什么考虑？如果并发量上来，可能会阻塞事件循环。
# 坏：这里不应该用 sync 方式读文件。
```

### 分级标注

- **[必须修复]** — 安全漏洞、数据丢失风险、逻辑错误（不修不能合）
- **[建议修改]** — 性能问题、可维护性、缺少校验（本次或下次迭代修复）
- **[仅供参考]** — 命名优化、风格建议、替代方案（不改也行）
- **[问题]** — 不确定的地方，需要作者解释意图

### 审查评论模板

```
[必须修复] SQL 注入风险

第 42 行：用户输入直接拼接到 SQL 语句中。

原因：攻击者可以通过 name 参数注入恶意 SQL。

建议：使用参数化查询：
  db.query('SELECT * FROM users WHERE name = $1', [name])

参考：https://cheatsheetseries.owasp.org/...
```

## 中英混排注释规范

### 何时用中文

业务逻辑说明、复杂算法注释、TODO/FIXME、内部项目文档注释（JSDoc/Javadoc 描述文字）：

```typescript
/**
 * 计算用户的会员等级折扣
 * 业务规则：普通会员 9.5 折、银卡 9 折、金卡 8.5 折、钻石 8 折
 * @param level - 会员等级（MemberLevel enum）
 * @param amount - 原始金额（单位：分）
 * @returns 折后金额（单位：分）
 */
function calculateDiscount(level: MemberLevel, amount: number): number { ... }
```

### 何时用英文

变量名/函数名/类名（始终英文）、开源项目注释、生产环境 error message（避免编码问题）、对外 API 文档。

### 混排格式

中英文之间加空格，技术术语保留英文。`使用 Redis 缓存` ✓，`使用Redis缓存` ✗。不强行翻译术语：`debounce 防抖` ✓，`防抖动处理` ✗。

## 常见反模式与对策

**反模式一：过度客气。** 所有评论都是"我觉得可能也许……"。对策：使用分级标注，[必须修复] 就是必须修复，语气温和但级别准确。

**反模式二：不敢给高级开发者提意见。** 直接用 Approve。对策：对事不对人，用提问式或学习式表达：
```
想请教一下，这里选择用递归而不是迭代，是出于什么考虑？如果深度超过 1000 层会不会有栈溢出风险？
```

**反模式三：审查变成风格之争。** 纠结缩进、空格、花括号。对策：风格问题交给 ESLint/Prettier/gofmt。Code Review 聚焦逻辑、安全、性能。

**反模式四：只写"LGTM"。** 随手 Approve，无实质审查。对策：写出关注了哪些方面：
```
LGTM
审查了：并发安全（锁粒度合理）、错误处理（外部调用都有 handling）、向下兼容（新字段有默认值）。
[仅供参考] 第 78 行 `d` 可改为 `duration`。
```

## 审查流程

### 审查顺序

1. 架构层面 → 2. 正确性 → 3. 安全性 → 4. 性能 → 5. 可维护性 → 6. 风格（只关注工具无法自动处理的部分）

### 给出总结

审查结束后给出总结：整体评价（一句话）+ 值得学习处 + 主要问题列表（按优先级）+ 建议修改方向。

```
总结：整体实现思路清晰，支付回调的幂等处理很到位。

主要问题：
1. [必须修复] 并发写 map（2 处）
2. [建议修改] 缺少空值校验（3 处）
3. [仅供参考] 几个变量命名可更语义化

建议先修复并发问题，校验部分可以本次一起改或拆到下个迭代。
```

## 检查清单

- [ ] 每条评论都标注了优先级
- [ ] [必须修复] 的问题都给出了具体修复建议
- [ ] 没有因面子跳过关键问题
- [ ] 没有纠结工具能自动处理的风格问题
- [ ] 对好的代码给予了肯定
- [ ] 给出了整体总结
