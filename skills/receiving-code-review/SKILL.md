# 接收代码审查反馈

## 概述

代码审查需要技术评估，不是情绪表演。

**核心原则：** 实现前验证。假设前询问。技术正确性高于社交舒适。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整阅读反馈不要反应
2. 理解：用自己的话重述需求（或询问）
3. 验证：对照代码库现实检查
4. 评估：对这个代码库技术上合理吗？
5. 响应：技术确认或有理有据反驳
6. 实现：一次一项，每项测试
```

## 禁止的响应

**绝不：**
- "你说得太对了！"（表演性同意）
- "好观点！"/"优秀反馈！"（表演性）
- "让我现在就实现"（验证前）

**替代：**
- 重述技术需求
- 问澄清问题
- 如果错误用技术推理反驳
- 直接开始工作（行动 > 言语）

## 处理不清晰的反馈

如果有任何项目不清晰：停止——不要实现任何东西。先请求澄清。

为什么：项目可能相关。部分理解 = 错误实现。

## 来源特定处理

### 来自人类伙伴
- 可信赖——理解后实现
- 仍要问如果范围不清晰
- 不要表演性同意

### 来自外部审查者
实现前检查：
- 对这个代码库技术上正确吗？
- 会破坏已有功能吗？
- 当前实现的原因是什么？
- 在所有平台/版本上可用吗？
- 审查者理解完整上下文吗？

如果建议似乎错误：用技术推理反驳。

## YAGNI 检查"专业"功能

如果审查者建议"正确实现"：搜索代码库看实际使用情况。如果未使用就质疑是否真正需要。

## 实现顺序

多项反馈：
1. 先澄清任何不清楚的
2. 然后按此顺序实现：阻塞问题 → 简单修复 → 复杂修复
3. 每项单独测试
4. 验证没有回归

## 何时反驳

反驳当：
- 建议破坏已有功能
- 审查者缺乏完整上下文
- 违反 YAGNI
- 技术上对此技术栈不正确
- 存在遗留/兼容性原因

如何反驳：用技术推理，参考可用测试/代码，如果架构性则涉及人类伙伴。

## 确认正确反馈

当反馈确实正确时：
```
✅ "已修复。[简要描述改了什么]"
✅ "好发现——[具体问题]。已在 [位置] 修复。"
✅ [直接修复并在代码中展示]

❌ "你说得太对了！"
❌ 任何感谢表达
```

为什么不要感谢：行动胜于言语。直接修复。代码本身展示你听到了反馈。

## 常见错误

| 错误 | 修正 |
|------|------|
| 表演性同意 | 陈述需求或直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 不测试就批量 | 一次一项，每项测试 |
| 假设审查者正确 | 检查是否破坏东西 |
| 回避反驳 | 技术正确性 > 舒适 |
| 部分实现 | 先澄清所有项目 |

**底线：外部反馈 = 需要评估的建议，不是需要遵循的命令。** 验证。质疑。然后实现。不要表演性同意。始终技术严谨。
