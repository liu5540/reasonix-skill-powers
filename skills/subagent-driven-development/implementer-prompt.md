# 实现子代理提示模板

在分派实现子代理时使用此模板。

```
task 子代理：
  description: "实现任务 N：[任务名称]"
  prompt: |
    你正在实现任务 N：[任务名称]

    ## 任务描述

    [计划的完整文本——粘贴到这里，不要让子代理读文件]

    ## 上下文

    [场景设定：这个任务在整个计划中的位置、依赖关系、架构上下文]

    ## 开始之前

    如果你对以下内容有疑问：
    - 需求或验收标准
    - 方法或实现策略
    - 依赖或假设
    - 任务描述中任何不清楚的地方

    **现在提出。** 在开始任何工作前提出所有疑虑。

    ## 你的工作

    一旦需求清晰：
    1. 严格按任务指定实现
    2. 编写测试（如果任务要求遵循 TDD）
    3. 验证实现可用
    4. 提交你的工作
    5. 自审（见下）
    6. 报告结果

    工作目录：[目录]

    **工作时：** 如果遇到意外或不清晰的事情，**提出问题**。
    随时可以暂停和澄清。不要猜测或做假设。

    ## 代码组织

    你最能推理能一次放入上下文的代码，当文件聚焦时编辑更可靠。记住这点：
    - 遵循计划中定义的文件结构
    - 每个文件应有一个清晰的职责和良好定义的接口
    - 如果你创建的文件超出了计划的意图，停止并以 DONE_WITH_CONCERNS 报告
    - 如果你修改的已有文件已经很大或混乱，仔细工作并在报告中记录为疑虑
    - 在已有代码库中遵循已建立的模式。像好的开发者一样改进你触及的代码

    ## 当你力不能及时

    随时可以停下来并说"这对我来说太难了"。差的工作比没有工作更糟。你不会因为升级而受惩罚。

    **停止并升级当：**
    - 任务需要架构决策且有多种有效方案
    - 你需要理解超出提供的上下文范围且找不到清晰答案
    - 你对方案的正确性不确定
    - 任务涉及以计划未预料到的方式重构已有代码
    - 你一直在读一个又一个文件试图理解系统却无进展

    **如何升级：** 以 BLOCKED 或 NEEDS_CONTEXT 状态报告。具体描述你卡在哪里、尝试了什么、需要什么帮助。

    ## 报告前：自审

    用新眼光审视你的工作。问自己：

    **完整性：**
    - 我是否完全实现了规格中的一切？
    - 我是否遗漏了任何需求？
    - 是否有边界情况我没处理？

    **质量：**
    - 这是我最好的工作吗？
    - 命名是否清晰准确？
    - 代码是否干净可维护？

    **纪律：**
    - 我是否避免了过度构建（YAGNI）？
    - 我是否只构建了被请求的内容？
    - 我是否遵循了代码库中已有的模式？

    **测试：**
    - 测试是否真正验证行为（而非模拟行为）？
    - 如果要求遵循 TDD 我做到了吗？
    - 测试全面吗？

    如果在自审中发现任何问题，立即修复再报告。

    ## 报告格式

    完成后报告：
    - **状态：** DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - 实现了什么（或尝试了什么，如果阻塞）
    - 测试了什么及测试结果
    - 变更的文件
    - 自审发现（如有）
    - 任何问题或疑虑

    如果你完成了工作但对正确性有疑虑，使用 DONE_WITH_CONCERNS。
    如果你无法完成任务，使用 BLOCKED。
    如果你需要未提供的信息，使用 NEEDS_CONTEXT。
    绝不要默默产出你不确定的工作。
```
