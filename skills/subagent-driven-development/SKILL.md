# 子代理驱动开发

通过为每个任务分派全新子代理来执行计划，每任务后进行两阶段审查：先规格合规审查，再代码质量审查。

**为什么用子代理：** 你将任务委托给拥有隔离上下文的专门代理。通过精确构建它们的指令和上下文，确保它们保持聚焦并成功完成任务。它们永远不应继承你的会话上下文或历史——你精确构建它们所需的内容。这也能保留你自己的上下文用于协调工作。

**核心原则：** 每任务全新子代理 + 两阶段审查（先规格再质量）= 高质量、快速迭代

**持续执行：** 不要在任务间暂停检查你的人类伙伴。连续执行计划中的所有任务。唯一停止的理由是：无法解决的 BLOCKED 状态、真正阻碍进展的歧义、或所有任务完成。"我应该继续吗？"这样的提示和进度摘要浪费他们时间——他们让你执行计划，所以执行。

## 何时使用

- 有实现计划？
  - 是 → 任务大多独立？→ 是 → 使用 subagent-driven-development
  - 否 → 先头脑风暴出计划
  - 任务紧密耦合 → 使用 executing-plans

## 过程

```
读取计划，提取所有任务完整文本，记录上下文，创建 todo_write
  ↓
对每个任务：
  ├─ 分派实现子代理（提供完整任务文本 + 上下文）
  ├─ 子代理提问？→ 是 → 回答问题后重新分派
  ├─ 子代理实现、测试、提交、自审
  ├─ 分派规格审查子代理
  ├─ 规格合规？→ 否 → 实现者修复后重新审查
  ├─ 分派代码质量审查子代理
  ├─ 质量批准？→ 否 → 实现者修复后重新审查
  ├─ 标记任务完成
  ↓
所有任务完成 → 分派最终代码审查 → 使用 finishing-a-development-branch
```

## 模型选择

使用每个角色所需的最弱模型以节约成本和提速。

**机械实现任务**（隔离函数、清晰规格、1-2 个文件）：使用快速便宜的模型。当计划良好指定时，大多数实现任务属于机械性任务。

**集成和判断任务**（多文件协调、模式匹配、调试）：使用标准模型。

**架构、设计和审查任务**：使用最有能力的模型。

**任务复杂度信号：**
- 触及 1-2 文件且有完整规格 → 便宜模型
- 触及多文件有集成问题 → 标准模型
- 需要设计判断或广泛的代码库理解 → 最强模型

## 处理实现者状态

实现子代理报告四种状态之一。分别处理：

**DONE：** 进行规格合规审查。

**DONE_WITH_CONCERNS：** 实现者完成了工作但标记了疑虑。先阅读疑虑再继续。如果疑虑关于正确性或范围，在审查前处理。如果只是观察（如"这个文件变大了"），记录下来并继续审查。

**NEEDS_CONTEXT：** 实现者需要未提供的信息。提供缺失的上下文后重新分派。

**BLOCKED：** 实现者无法完成任务。评估阻塞：
1. 如果是上下文问题，提供更多上下文并用相同模型重新分派
2. 如果任务需要更多推理，用更强的模型重新分派
3. 如果任务太大，拆成更小的部分
4. 如果计划本身有误，升级给人类

**绝不**忽略升级或强制相同模型重试而不做改变。如果实现者说卡住了，某些东西需要改变。

## 红线

**绝不：**
- 在 main/master 分支上开始实现（除非用户明确同意）
- 跳过审查（规格或代码质量）
- 带着未修复的问题继续
- 并行分派多个实现子代理（冲突）
- 让子代理读取计划文件（提供完整文本）
- 跳过场景设定上下文
- 忽略子代理的问题
- 接受"差不多"的规格合规
- 跳过审查循环
- 在规格合规通过前开始代码质量审查
- 在任一审查仍有未解决问题时移动到下一任务

**如果子代理提问：** 清晰完整回答。如果子代理失败：分派修复子代理给出具体指令。

## 集成

**必需工作流技能：**
- **brainstorming** — 创建规格/设计
- **writing-plans** — 创建此技能执行的计划
- **requesting-code-review** — 审查子代理的代码审查模板
- **finishing-a-development-branch** — 所有任务完成后完成开发

**子代理应使用：**
- **test-driven-development** — 子代理对每个任务遵循 TDD
