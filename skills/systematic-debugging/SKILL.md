# 系统性调试

## 概述

随机修复浪费时间并制造新 Bug。快速补丁掩盖深层问题。

**核心原则：** 在尝试修复前始终找到根因。治标是失败。

**违反此过程的字面就是在违反调试的精神。**

## 铁律

```
未完成根因调查前不写修复
```

如果没有完成第1阶段，你不能提出修复。

## 何时使用

适用于任何技术问题：
- 测试失败
- 生产 Bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况使用：**
- 时间压力下（紧急情况让猜测很诱人）
- "快速修复"看起来很明显
- 你已经尝试了多次修复
- 之前的修复没起作用
- 你没有完全理解问题

## 四阶段过程

### 第1阶段：根因调查

**在尝试任何修复前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们通常包含精确的解决方案
   - 完整阅读堆栈跟踪
   - 记录行号、文件路径、错误代码

2. **一致复现**
   - 你能可靠触发吗？
   - 精确步骤是什么？
   - 每次都发生吗？
   - 如果不能复现 → 收集更多数据，不要猜测

3. **检查最近变更**
   - 什么变更可能导致这个？
   - Git diff、最近提交
   - 新依赖、配置变更
   - 环境差异

4. **在多组件系统中收集证据**
   - 在每个组件边界记录输入/输出
   - 验证环境/配置传播
   - 检查每层状态
   - 运行一次收集证据展示在哪里出问题

5. **追踪数据流**
   - 坏值从哪里来？
   - 谁用坏值调用了这个？
   - 持续向上追踪直到找到源头
   - 在源头修复，不在症状处修复

### 第2阶段：模式分析

1. **找到可用示例** — 在相同代码库中定位类似的可工作代码
2. **对照参考对比** — 完整阅读参考实现，不要略读
3. **识别差异** — 列出可工作与不可工作之间的每个差异
4. **理解依赖** — 这个组件还需要什么？

### 第3阶段：假设与测试

1. **形成单一假设** — 清晰陈述："我认为 X 是根因因为 Y"
2. **最小化测试** — 做最小可能的变更来测试假设
3. **验证后再继续** — 有效？→ 第4阶段。无效？→ 形成新假设。不要在上面叠加更多修复
4. **当你不懂时** — 说"我不理解 X"。不要假装知道

### 第4阶段：实现

1. **创建失败测试用例** — 使用 `test-driven-development` 技能
2. **实现单一修复** — 一次一个变更
3. **验证修复** — 测试通过？其他测试没坏？
4. **如果修复无效** — 停止。如果 <3 次尝试：回到第1阶段。如果 ≥3 次：**质疑架构**

**如果3+次修复失败：质疑架构**
- 每个修复揭示新的共享状态/耦合/问题 → 停止并质疑基础
- 这个模式根本上合理吗？
- 是否应该重构架构而非继续修复症状？
- **与人类伙伴讨论后再尝试更多修复**

## 红线 — 停止并遵循过程

- "快速修复现在，稍后调查"
- "试试改 X 看能不能用"
- "加多个变更，跑测试"
- "跳过测试，我手动验证"
- "大概率是 X，让我修"
- "我不完全理解但这可能有用"
- "再来一次修复尝试"（已尝试2+次）
- 每个修复揭示不同地方的新问题

**所有这些意味着：停止。回到第1阶段。**

## 常见合理化

| 借口 | 现实 |
|------|------|
| "问题简单不需要过程" | 简单问题也有根因。过程对简单Bug很快。 |
| "紧急没时间走过程" | 系统性调试比猜测试错更快。 |
| "先试试这个再调查" | 第一个修复设定模式。从一开始就做对。 |
| "确认修复有效后再写测试" | 未测试的修复不稳定。先测试证明它。 |
| "多个修复一起做节省时间" | 无法隔离哪个有效。制造新Bug。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因** | 读错误、复现、检查变更、收集证据 | 理解是什么和为什么 |
| **2. 模式** | 找可用示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实现** | 创建测试、修复、验证 | Bug已解决、测试通过 |
