# 系统化调试

## 概述

随意修复既浪费时间又引入新 bug。草率补丁只会掩盖深层问题。

**核心原则：** 在尝试修复之前，务必先找到根本原因。只修症状就是失败。

**敷衍走流程等于违背调试的精神。**

## 铁律

不做根因调查，不许提修复方案。没完成第一阶段就不能提出修复方案。

## 何时使用

任何技术问题：测试失败、生产环境 bug、异常行为、性能问题、构建失败、集成问题。尤其在时间紧迫、觉得"一个小修改就能搞定"、已经尝试多种修复、上次修复没生效时**必须使用**。问题看起来简单也不要跳过。

## 四个阶段

### 第一阶段：根因调查（在尝试任何修复之前）

1. **仔细阅读错误信息** — 用 `read_file` 阅读完整错误日志/堆栈跟踪，不跳过错误或警告，记下行号、文件路径、错误码
2. **稳定复现** — 能可靠触发吗？每次都能复现？无法复现则收集更多数据，不猜测
3. **检查近期变更** — `git diff` 查看工作区变更、`git log --oneline -10` 查看近期提交、`search_content` 检查相关代码、新依赖/配置变更/环境差异
4. **在多组件系统中收集证据** — 对每个组件边界记录进入和离开的数据，验证环境/配置传递，确定断裂点后针对该组件深入调查
5. **跟踪数据流** — 错误值从哪里产生？谁用错误值调用了这里？持续向上追踪直到找到源头。在源头修复，不在症状处修复

参见本目录下 `root-cause-tracing.md` 了解完整反向追踪技术。

### 第二阶段：模式分析

1. **找到可正常工作的示例** — 用 `search_content` 找到类似正常代码，用 `read_file` 完整阅读参考实现
2. **与参考实现对比** — 逐行阅读，彻底理解后再应用
3. **识别差异** — 列出每个差异，不假设"那不可能有影响"
4. **理解依赖关系** — 需要哪些其他组件、配置、环境？有哪些隐含假设？

### 第三阶段：假设与验证

1. **提出单一假设** — 清晰陈述"我认为 X 是根本原因，因为 Y"
2. **最小化测试** — 最小改动验证假设，每次只改一个变量
3. **继续之前先验证** — 生效则进入第四阶段；没生效则提出新假设；不叠加修复
4. **不确定时** — 说"我不理解 X"，不假装知道，寻求帮助

### 第四阶段：实施

1. **创建失败的测试用例** — 最简化复现，使用 test-driven-development 编写规范的失败测试
2. **实施单一修复** — 修复已定位的根本原因，每次只改一处，不做"顺便改改"，不捆绑重构
3. **验证修复** — 测试通过？其他测试未被破坏？问题真的解决了？
4. **修复不起作用时** — 少于 3 次：回到第一阶段；3 次或以上：停下来质疑架构
5. **3 次以上修复失败 → 质疑架构** — 架构问题信号：每次修复暴露新问题、修复需要"大规模重构"、每次修复在其他地方产生新症状。和搭档讨论后再继续。

## 红线 — 停下来，回到第一阶段

- "先临时修一下，以后再排查"
- "试着改改 X 看看行不行"
- "一次性改多个地方，跑测试看看"
- "跳过测试，我手动验证"
- "大概是 X 的问题，让我修一下"
- "我不完全理解，但这应该能行"
- 没有追踪数据流就提出解决方案
- "再试一次修复"（已尝试 2 次以上）
- 每次修复都暴露出不同地方的新问题

## 常见借口

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要走流程" | 简单问题也有根因。简单 bug 流程很快。 |
| "紧急情况，没时间走流程" | 系统化调试比反复猜测式修复更快。 |
| "先试一下，再排查" | 第一次修复定下基调。从一开始就做对。 |
| "确认修复有效后再写测试" | 没有测试的修复留不住。先写测试证明修复有效。 |
| "一次修多个问题省时间" | 无法隔离哪个生效，还会引入新 bug。 |
| "我看出问题了，让我修一下" | 看到症状 ≠ 理解根因。 |
| "再试一次"（2 次以上失败后） | 3 次以上失败 = 架构问题。质疑模式。 |

## 速查表

| 阶段 | 关键活动 | 通过标准 |
|------|---------|---------|
| 1. 根因 | 阅读错误、复现、检查变更、收集证据 | 理解了什么出了问题以及为什么 |
| 2. 模式 | 找到正常示例、对比 | 识别出差异 |
| 3. 假设 | 提出理论、最小化验证 | 假设被验证或产生新假设 |
| 4. 实施 | 创建测试、修复、验证 | bug 已修复，测试通过 |

找不到根因时：记录排查了什么 → 实施处理措施（重试、超时、错误提示）→ 添加监控/日志。但 95% 的"找不到根因"其实是排查不充分。
