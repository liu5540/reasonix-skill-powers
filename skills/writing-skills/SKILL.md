# 编写技能

## 概述

编写技能 = 将 TDD 应用于流程文档。写测试（压力场景）→ 观察失败（基线）→ 写技能（文档）→ 观察通过（遵守）→ 重构（堵漏洞）。

**核心原则：** 没观察到智能体在没有技能时失败，就不知道技能教了正确的东西。

**必需背景：** test-driven-development。

## 什么是技能

技能是经过验证的技术/模式/工具的参考指南。是：可复用的技术、模式、工具。不是：一次性的叙事。

## 何时创建

创建：技术非直觉、会反复引用、广泛适用、他人受益。不创建：一次性方案、标准实践有文档、项目特定约定（放 AGENTS.md）、机械性约束可用正则强制执行。

## 目录结构

```
skills/
  skill-name/
    SKILL.md              # 主文档（必需）
    supporting-file.*     # 仅在需要时（参考 > 100行 或 可复用工具）
```

## SKILL.md 结构

**Frontmatter（YAML）：**
- 必需：`name`（字母、数字、连字符）、`description`（最多 1024 字符）
- `description`：第三人称，"Use when..."开头，只描述触发条件/症状，**绝不总结流程**
- 尽量控制在 500 字符以内

**正文结构：**
```markdown
# 技能名称

## 概述
1-2 句话核心原则。

## 何时使用
症状和用例列表；不适用场景。

## 核心模式 / 工作步骤
前后对比或编号步骤。

## 快速参考 / 红线
要点列表或表格。

## 常见错误
常见问题 + 修复。

## 前置与后续步骤（如有）

写明谁调用你、你调用谁、具体用什么命令。不要只列技能名——Reasonix 不会自动触发。例如：`完成后调用 run_skill(name="finishing-a-development-branch") 收尾。`
```

## 搜索优化

**描述字段：** 描述 = 何时使用，不是做什么。描述总结工作流时 AI 可能跟描述走而不读内容。描述问题（竞态条件、不一致）而非语言症状。第三人称。

**关键词覆盖：** 用 AI 会搜索的词：错误信息、症状（"flaky"、"hanging"）、同义词、工具名。

**命名：** 动词优先，主动语态。`creating-skills` ✓，`skill-creation` ✗。

**Token 效率：** 入门工作流 < 150 词、频繁加载 < 200 词、其他 < 500 词。技巧：参数详情移 `--help`、交叉引用不重复细节、一个优秀示例胜过多个平庸、不解释命令能看出的东西。

**交叉引用：** 只用技能名称。`**必需：** test-driven-development` ✓，`@skills/testing/...` ✗。

## 铁律

没有失败的测试就不写技能。先写技能再测试？删掉，重新开始。编辑技能不测试？同样违规。

**无例外：** 不适用"简单添加"、"加一个章节"、"文档更新"。不留未测试更改作"参考"。删除就是删除。

## 让技能抵抗合理化

**堵漏洞：** 不只陈述规则，禁止具体变通方法。`不要保留作为"参考"`、`不要"改编"`。

**精神 vs 字面：** 在前面加入 `**违反规则的字面意思就是违反规则的精神。**`

**合理化借口表：** 从基线测试捕获每个借口，逐一反驳。

**红线列表：** 列出"意味着删除代码，从头开始"的行为清单。

## 红-绿-重构（技能版）

**红（基线）：** 无技能时运行压力场景，逐字记录行为、合理化借口、违规触发点。

**绿（最小技能）：** 针对具体借口编写技能，不为假设情况添加内容。同样场景应遵守。

**重构（堵漏洞）：** 发现新借口 → 添加明确反驳 → 重测直到无懈可击。

测试方法详见 `testing-skills-with-subagents.md`。

## 测试所有技能类型

| 类型 | 测试方式 | 成功标准 |
|------|----------|----------|
| 纪律执行类 | 学术性问题 + 压力场景 + 多重压力 | 最大压力下遵循规则 |
| 技术类 | 应用场景 + 变体 + 缺失信息测试 | 成功应用于新场景 |
| 模式类 | 识别场景 + 应用 + 反例 | 正确识别何时/如何应用 |
| 参考类 | 检索场景 + 应用 + 覆盖测试 | 找到并正确应用 |

## 反模式

叙事式示例（"在某次会话中……"）— 太具体不可复用。多语言稀释 — 质量平庸维护重。流程图中的代码 — 无法复制。通用标签（helper1、step3）— 无语义意义。

## 部署

写完技能后停下完成部署流程。不批量创建不测试。部署未测试技能 = 部署未测试代码。

## 技能创建清单

**红 — 编写失败测试：**
- [ ] 创建压力场景（纪律类 3+ 组合压力）
- [ ] 无技能运行 — 逐字记录基线
- [ ] 识别合理化借口模式

**绿 — 编写最小技能：**
- [ ] 名称只使用字母、数字、连字符
- [ ] YAML frontmatter 有 `name` 和 `description`（最多 1024 字符）
- [ ] 描述 "Use when..." 开头 + 具体触发条件
- [ ] 描述第三人称，不总结工作流
- [ ] 全文含搜索关键词
- [ ] 清晰概述带核心原则
- [ ] 解决红色阶段的具体基线失败
- [ ] 一个优秀示例（非多语言）
- [ ] 用技能运行 — 验证遵守

**重构 — 堵漏洞：**
- [ ] 识别新借口
- [ ] 添加明确反驳（纪律类）
- [ ] 创建红线列表
- [ ] 重测直到无懈可击

**质量检查：**
- [ ] 非明显决策点用小流程图
- [ ] 快速参考 + 常见错误章节
- [ ] 无叙事性故事

**部署：**
- [ ] 提交到 git
