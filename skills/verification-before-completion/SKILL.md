# 完成前验证

## 概述

没有验证就宣称完成不是高效，是不诚实。

**核心原则：** 始终用证据支撑结论。敷衍这条规则等于违背它的精神。

## 铁律

没有新鲜的验证证据，不许宣称完成。没运行验证命令就不能声称测试通过。

## 门控流程

宣称任何状态之前：

1. **确定** — 什么命令能证明这个结论？
2. **运行** — 执行完整命令（重新运行，完整执行）
3. **阅读** — 完整输出，检查退出码，统计失败数
4. **验证** — 输出支持结论吗？否则用证据说明实际状态
5. **只有这时** — 才能做出结论

跳过任何一步 = 说谎，不是验证。

## 常见失败模式

| 结论 | 需要 | 不够格 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 failures | 之前的运行结果、"应该会通过" |
| Linter 无报错 | Linter 输出：0 errors | 部分检查、推断 |
| 构建成功 | 构建命令：exit 0 | linter 通过 |
| Bug 已修复 | 测试原始症状：通过 | 代码改了，假设已修复 |
| 代理已完成 | VCS diff 显示变更 | 代理报告"成功" |
| 需求已满足 | 逐项核对清单 | 测试通过 |

## 红线

使用"应该"、"大概"、"似乎"、验证前就表达满意（"太好了！"、"搞定！"）、即将提交/推送/创建 PR 却没有验证、信任代理的成功报告、依赖部分验证、想着"就这一次"——全部停下来，运行验证。

## 关键模式

测试：`run_command(command="go test ./...")` → 看到 34/34 pass → "全部测试通过"。不说"应该能通过了"。

回归测试（TDD 红-绿）：编写测试 → 运行通过 → 回退修复 → 运行必须失败 → 恢复 → 运行通过。不说"我写了回归测试"但没有红-绿验证。

构建：`run_command(command="go build ./...")` → exit 0 → "构建通过"。Linter 通过 ≠ 编译通过。

代理委派：代理报告成功 → `git diff` 检查 VCS diff → 验证变更。不信任代理报告。

## 防止合理化

| 借口 | 现实 |
|------|------|
| "应该能行了" | 运行验证命令 |
| "我有信心" | 信心 ≠ 证据 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "代理说成功了" | 独立验证 |
| "部分检查就够了" | 部分检查什么也证明不了 |

## 底线

验证没有捷径。运行命令，阅读输出，然后才能宣称结果。没有商量余地。
