# 完成前验证

## 概述

声称工作完成而不验证是不诚实，不是效率。

**核心原则：** 永远先有证据再断言。

违反此规则的字面就是在违反此规则的精神。

## 铁律

```
没有新鲜验证证据不做完成声明
```

如果你没在此消息中运行验证命令，你不能声称它通过。

## 门函数

```
在声明任何状态或表达满意之前：

1. 识别：什么命令能证明这个声明？
2. 运行：执行完整命令（新鲜、完整）
3. 读取：完整输出，检查退出码，数失败数
4. 验证：输出确认声明吗？
   - 如果否：用证据陈述实际状态
   - 如果是：陈述声明带上证据
5. 只有这时：做出声明

跳过任何步骤 = 撒谎，不是验证
```

## 常见失败

| 声明 | 需要 | 不够 |
|------|------|------|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行、"应该通过" |
| Linter 干净 | Linter 输出：0 错误 | 部分检查、推测 |
| 构建成功 | 构建命令：exit 0 | Linter 通过、日志看起来好 |
| Bug 已修复 | 测试原始症状：通过 | 代码改了、假设修好了 |
| 回归测试可用 | 红绿循环已验证 | 测试通过一次 |
| 代理完成 | VCS diff 显示变更 | 代理报告"成功" |
| 需求已满足 | 逐行检查清单 | 测试通过 |

## 红线 — 停止

- 使用"应该"、"大概率"、"好像"
- 验证前表达满意（"太好了！"、"完美！"、"搞定！"等）
- 即将提交/推送/PR 而不验证
- 信任代理成功报告
- 仅依靠部分验证
- 想"就这一次"
- 累了想快点结束工作
- **任何暗示成功但没有运行验证的措辞**

## 合理化预防

| 借口 | 现实 |
|------|------|
| "现在应该能用了" | 运行验证 |
| "我相信" | 信心 ≠ 证据 |
| "就这一次" | 没有例外 |
| "Linter 通过了" | Linter ≠ 编译器 |
| "代理说成功" | 独立验证 |
| "我累了" | 疲惫 ≠ 借口 |
| "部分检查就够了" | 部分不能证明任何东西 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到: 34/34 pass] "所有测试通过"
❌ "应该通过了" / "看起来正确"
```

**回归测试（TDD 红绿）：**
```
✅ 写 → 运行(pass) → 回退修复 → 运行(必须FAIL) → 恢复 → 运行(pass)
❌ "我写了一个回归测试"（没有红绿验证）
```

**代理委托：**
```
✅ 代理报告成功 → 检查 VCS diff → 验证变更 → 报告实际状态
❌ 信任代理报告
```

## 何时应用

**始终在以下之前：**
- 任何成功/完成声明的变体
- 任何表达满意
- 任何关于工作状态的正面陈述
- 提交、创建 PR、任务完成
- 移动到下一任务
- 委托给代理

**底线：验证没有捷径。** 运行命令。读取输出。然后声明结果。不容协商。
