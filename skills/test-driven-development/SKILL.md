# 测试驱动开发（TDD）

## 概述

先写测试。看着它失败。写最小代码使其通过。

**核心原则：** 如果你没看到测试失败，你就不知道它是否测试了正确的东西。

**违反规则的字面就是在违反规则的精神。**

## 何时使用

**总是：**
- 新功能
- Bug 修复
- 重构
- 行为变更

**例外（询问你的人类伙伴）：**
- 一次性原型
- 生成的代码
- 配置文件

在想"就这一次跳过 TDD"？停下。那是合理化。

## 铁律

```
没有先写失败的测试，不写生产代码
```

测试之前写的代码？删掉。重新开始。

**没有例外：**
- 不要留作"参考"
- 不要"边写测试边改"
- 不要看
- 删掉就是删掉

从零开始基于测试实现。句号。

## 红-绿-重构

```
RED（红）→ 验证失败 → GREEN（绿）→ 验证通过 → REFACTOR（重构）→ 保持绿色 → 下一轮
```

### RED — 写失败的测试

写一个最小测试展示应该发生什么。

**好例子：**
```go
func Test重试失败操作3次(t *testing.T) {
    attempts := 0
    operation := func() (string, error) {
        attempts++
        if attempts < 3 {
            return "", errors.New("失败")
        }
        return "成功", nil
    }
    result, err := RetryOperation(operation)
    if err != nil || result != "成功" {
        t.Errorf("期望成功，得到 %v, %v", result, err)
    }
    if attempts != 3 {
        t.Errorf("期望重试3次，实际 %d 次", attempts)
    }
}
```
清晰命名、测试真实行为、一件事

**坏例子：**
```go
func Test重试(t *testing.T) {
    // 使用 mock 测试模拟行为
}
```
模糊命名、测试 mock 而非代码

**要求：**
- 一个行为
- 清晰命名
- 真实代码（除非不可避免否则不用 mock）

### 验证 RED — 看它失败

**强制步骤。绝不跳过。**

```bash
go test ./pkg/path/ -run TestName -v
```

确认：
- 测试失败（不是错误）
- 失败消息符合预期
- 失败是因为功能缺失（不是拼写错误）

**测试通过？** 你在测试已有行为。修改测试。

**测试报错？** 修复错误，重新运行直到正确失败。

### GREEN — 最小代码

写最简单的代码使测试通过。

**好例子：**
```go
func RetryOperation(fn func() (string, error)) (string, error) {
    for i := 0; i < 3; i++ {
        result, err := fn()
        if err == nil {
            return result, nil
        }
    }
    return "", errors.New("操作失败")
}
```
刚好够通过

**坏例子：** 添加 options、backoff 策略、回调函数等（YAGNI——你不需要它们）

不要添加功能、不要重构其他代码、不要"超出测试改进"。

### 验证 GREEN — 看它通过

**强制步骤。**

```bash
go test ./pkg/path/ -run TestName -v
```

确认：
- 测试通过
- 其他测试仍然通过
- 输出干净（无错误、警告）

**测试失败？** 修复代码，不是测试。

**其他测试失败？** 立即修复。

### REFACTOR — 清理

仅在绿色之后：
- 消除重复
- 改进命名
- 提取辅助函数

保持测试绿色。不要添加行为。

### 重复

下一个失败测试对应下一个功能。

## 好测试的特征

| 质量 | 好 | 坏 |
|------|-----|-----|
| **最小** | 一件事。名字里有"和"？拆分。 | `Test验证邮箱和域名和空格` |
| **清晰** | 名字描述行为 | `Test测试1` |
| **展示意图** | 演示期望 API | 掩盖代码应该做什么 |

## 为什么顺序重要

**"我后面会写测试来验证它可用"**
实现后写的测试立即通过。立即通过说明不了任何问题——可能测试了错误的东西、实现细节而非行为、遗漏边界情况、你从未看到它捕获 Bug。

**"我已经手动测试了所有边界情况"**
手动测试是临时的不是系统性的。没有记录、代码变更后不能重新运行、压力下容易忘记案例。

## 常见合理化

| 借口 | 现实 |
|------|------|
| "太简单不需要测试" | 简单代码也会坏。测试只需30秒。 |
| "我后面测试" | 立即通过的测试说明不了任何东西。 |
| "后面测试达到同样目标" | 后测=代码在做什么；先测=代码应该做什么。 |
| "已经手动测试过" | 临时≠系统。无记录，不能重跑。 |
| "已经花了几小时，删掉浪费" | 沉没成本谬误。保留未验证代码=技术债务。 |
| "留着做参考，先写测试" | 你会适应它。那就是后测。删掉就是删掉。 |
| "需要先探索" | 丢弃探索代码，用 TDD 重新开始。 |
| "测试难写=设计不清晰" | 倾听测试。难测=难用。 |
| "TDD 会拖慢我" | TDD 比调试快。务实=测试优先。 |

## 红线 — 停止并重新开始

- 代码在测试之前
- 实现后测试
- 测试立即通过
- 不能解释为什么测试失败
- "稍后"添加的测试
- 合理化"就这一次"
- "我已经手动测试过了"
- "后面测试达到同样目的"
- "这是关于精神不是仪式"
- "留着做参考"或"适配已有代码"
- "已经花了X小时，删除浪费"
- "TDD 是教条，我是务实"
- "这次不同因为……"

**所有这些意味着：删除代码。用 TDD 重新开始。**

## Bug 修复示例

**Bug：** 空邮箱被接受

**RED**
```go
func Test拒绝空邮箱(t *testing.T) {
    result := SubmitForm(FormData{Email: ""})
    if result.Error != "邮箱必填" {
        t.Errorf("期望 '邮箱必填'，得到 '%s'", result.Error)
    }
}
```

**验证 RED**
```bash
$ go test -run Test拒绝空邮箱
FAIL: 期望 '邮箱必填'，得到 ''
```

**GREEN**
```go
func SubmitForm(data FormData) Result {
    if strings.TrimSpace(data.Email) == "" {
        return Result{Error: "邮箱必填"}
    }
    // ...
}
```

**验证 GREEN**
```bash
$ go test -run Test拒绝空邮箱
PASS
```

**REFACTOR**
提取验证逻辑复用。

## 验证检查清单

标记工作完成前：

- [ ] 每个新函数/方法有测试
- [ ] 在实现前看了每个测试失败
- [ ] 每个测试因预期原因失败（功能缺失，而非拼写错误）
- [ ] 写最小代码使每个测试通过
- [ ] 所有测试通过
- [ ] 输出干净（无错误、警告）
- [ ] 测试使用真实代码（仅在不可避免时用 mock）
- [ ] 边界情况和错误已覆盖

不能勾选全部？你跳过了 TDD。重新开始。

## 最终规则

```
生产代码 → 测试存在且先失败
否则 → 不是 TDD
```

没有例外，除非你的人类伙伴允许。
